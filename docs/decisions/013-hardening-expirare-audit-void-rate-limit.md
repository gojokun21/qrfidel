# 013 – Hardening: expirări, `cards:recalculate`, audit append-only, void în UI, limitatori numiți

**Data:** 2026-10-16 · **Status:** acceptat

## Context
Sesiunea 10 (SDD §6, §8, §10) închide notele lăsate pentru „hardening”: joburile de expirare (`ExpireStamps`, `ExpireRewards`, `ExpireStampRequests`), comanda `cards:recalculate` (SDD §4), auditul complet, anularea din UI și rate limit-ul cu limitatori numiți. SDD nu spune ce înseamnă „ștampilele expiră după N zile” și nici cum intră expirările în jurnal.

## Decizie
- **Ștampilele expiră pe inactivitate** (ales cu utilizatorul): dacă un card nu primește nicio ștampilă `stamps_expire_days` zile (`last_stamp_at <= now − N zile`), soldul revine la 0 printr-o tranzacție `expire` (quantity = −sold, fără angajat și locație, `meta.balance_before/after`, `reason=inactivity`). Cheia de idempotency `expire:{card}:{last_stamp_at}` împiedică o expirare dublă. Afacerile suspendate nu se ating. Ștampilele anulate nu contează (void-ul mută `last_stamp_at` înapoi). O tranzacție `expire` blochează anularea ștampilei de dinaintea ei (regula „ultima ștampilă”, ADR 004).
- **Recompensele expirate nu intră în jurnal:** statusul devine `expired`, iar `rewards_available` se reface din registrul `rewards` (nu doar se scade – repară și un drift vechi). O tranzacție `expire` pentru recompense ar bloca anularea ultimei ștampilei. Audit `reward.expired` per card (`count`, `reward_ids`). Se aplică și afacerilor suspendate (recompensa era deja nefolosibilă prin `Reward::usable()`).
- **Cererile de la tejghea:** UPDATE în bloc pe `pending` cu `expires_at <= now` → `expired`, fără audit per rând. Postgres reverifică `status` după lock, deci o cerere aprobată între timp nu se atinge. Expirarea „leneșă” din ADR 012 rămâne (jobul e curățenie).
- **Joburi:** `ShouldQueue` + `ShouldBeUnique`, subțiri, logica în `ExpirationService`. Scheduler: cererile la 5 minute, recompensele și ștampilele orar, toate `onOneServer()` (cache cu lock-uri comune – Redis – în producție). Suprapunerea o previne `ShouldBeUnique`, cu `uniqueFor = 300` (un worker omorât în timpul jobului blochează cel mult 5 minute). Fiecare card în tranzacția lui, cu lock pe card și condiția reverificată sub lock; cardurile se parcurg cu `chunkById`.
- **Regulile de ordine ale void-ului** (ultima mișcare activă, recompensa emisă nefolosită) stau într-un singur loc, `VoidService::blockedStamps()`, folosit și de lista din dashboard.
- **`cards:recalculate {--card=} {--business=} {--dry-run}`** (`CardBalanceService`): `stamps_balance` = replay pe tranzacțiile active stamp/expire/adjust, folosind `meta.balance_after` unde există și regulile programului (`RewardRules::applyStamps()`, mutat din StampService) pentru rândurile vechi fără meta; `rewards_available` = recompensele `available`; `last_stamp_at` = ultima ștampilă neanulată. Nu scrie în jurnal; o corecție intră în audit (`card.recalculated`, before/after, actor sistem).
- **Audit:** actorul poate fi null (= sistem: joburi, recalculare). `ip_address` se completează pentru acțiunile venite printr-o rută web (în console/worker rămâne null). `audit_logs` devine append-only (gărzi pe model + trigger Postgres pe UPDATE/DELETE; TRUNCATE din testele de concurență nu e afectat). Pagina „Jurnal de activitate” (`/dashboard/audit`, doar owner): 50 pe pagină, filtru pe categorie; etichetele și categoriile stau în `App\Support\AuditActions` (un test verifică că fiecare acțiune scrisă de servicii are etichetă).
- **Void în UI:** pagina „Tranzacții” (`/dashboard/transactions`, manager+; managerul legat de o locație vede doar locația lui), filtre pe locație și tip, plus același formular în „Ultimele mișcări” de pe ecranul cardului (fără tichet de scanare, ADR 011). Butonul apare doar pe tranzacțiile anulabile: regulile simple din `VoidService::refusal()` (scoase din `assertVoidable`, fără duplicare) plus „ultima mișcare activă a cardului” și „recompensa emisă nefolosită”, calculate în bloc în `TransactionLog`. Un singur endpoint `POST /dashboard/transactions/{id}/void` (cheie UUID la randare, motiv opțional ≤ 200).
- **Limitatori numiți** (`config('loyalty.rate_limits')`): `staff-actions` 60/min per angajat (stamp, redeem, approve/reject, void), `customer-actions` 20/min per client (înscriere, cerere), `customer-qr`/`customer-status` (valorile din ADR 010/012), `magic-link-send`/`magic-link-consume` 10/min per IP (limita per email rămâne în serviciu), `invitation-register` 6/min per IP, `invitations` 20/oră per afacere (afacerea se rezolvă în limitator: throttle-ul rulează înaintea middleware-ului `business`). Rutele Breeze (`password.*`, `verification.*`) își păstrează throttle-ul numeric.
- **429:** JSON → `{message}` în română + `Retry-After`; formular (POST) → înapoi cu eroarea `loyalty`; pagină și formularele Breeze (`verification.*`, `password.*`, care nu afișează eroarea `loyalty`) → `errors/429` în română.

## Consecințe
- Pe un program cu `stamps_expire_days = 1`, o ștampilă expirată exact la 24h nu se mai poate anula (mesajul „Doar ultima ștampilă…”).
- Rapoartele (S11) trebuie să trateze `expire` ca mișcare de sold, nu ca ștampilă, iar recompensele expirate se citesc din `rewards`.
- În producție trebuie pornite scheduler-ul (`schedule:work` / cron) și un worker de cozi (S12).
